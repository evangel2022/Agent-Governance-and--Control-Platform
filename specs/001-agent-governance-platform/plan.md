# Implementation Plan: Agent Governance and Control Platform

**Branch**: `001-agent-governance-platform` | **Date**: 2026-10-13 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-agent-governance-platform/spec.md`

**Note**: This plan is filled in by the `$speckit-plan` command. It is a design
artifact; no application business code is generated by it.

## Summary

Build a private-deployable, enterprise-grade Agent governance and control plane
for ERP, finance and supply chain. The platform gives an organisation an
authoritative inventory of Agents, Tools and Models; evaluates every Agent tool
invocation against policy; requires accountable human approval for high-risk
operations; and records every governed action in a tamper-evident audit trail.

The first release is a runnable P1 loop (register → decide → approve → record)
delivered as a modular-monolith control plane plus two independently deployed
enforcement services: an MCP gateway that owns the invocation path, and an
isolated execution runtime for high-risk and untrusted work. React + TypeScript
SPA at the front; Python + FastAPI control plane; PostgreSQL as system of record;
Redis for cache, rate limiting and short-term workflow state; LangGraph for
multi-step agent workflows; OPA/Rego for policy-as-code; containers for
isolation, Docker Compose for development, and Helm on Kubernetes reserved for
on-premises production.

## Technical Context

**Language/Version**: Python 3.12 (control plane, gateway, runner, worker);
TypeScript 5.6 on Node.js 22 LTS (SPA and gateway tooling)

**Primary Dependencies**: FastAPI, Pydantic v2, SQLAlchemy 2.0 (async), Alembic,
asyncpg; React 18, Vite, TanStack Query, Ant Design; LangGraph; OPA (Rego);
MCP SDK; Keycloak (OIDC) for human identity; HashiCorp Vault (Transit + KV v2)
for secrets and key material; OpenTelemetry SDK

**Storage**: PostgreSQL 16 (system of record, row-level security for tenant
scoping); Redis 7 (cache, distributed locks, rate limits, Streams for the local
event bus); S3-compatible object storage (evaluation datasets, audit exports)

**Testing**: pytest + pytest-asyncio + httpx ASGI transport; testcontainers for
PostgreSQL, Redis and OPA; Schemathesis for contract tests generated from
OpenAPI; Vitest + React Testing Library; Playwright for E2E; k6 for load checks

**Target Platform**: Linux containers. Docker Compose for development and
single-node private installs; Kubernetes (Helm) for on-premises production with
a reserved profile for future managed cloud.

**Project Type**: Web application (FastAPI control plane + React SPA) with two
supporting services (MCP gateway, isolated runner) and one async worker.

**Performance Goals**: p95 policy decision < 150 ms; p95 control-plane read
< 300 ms; sustained 50 invocations/s with bursts to 200/s per deployment;
dashboard aggregates p95 < 2 s; audit search p95 < 2 s across 90 days. These
figures are the engineering budget that satisfies SC-011; the scale they assume
is headroom above the volume stated in the specification's Assumptions.

**Constraints**: fail closed when policy or approval decisions cannot be
evaluated; deny by default; organisation-scoped isolation enforced in the data
layer; no long-lived secrets in configuration; append-only tamper-evident audit;
all schema change via versioned migrations; must operate air-gapped with no
mandatory egress.

**Scale/Scope**: initial phase governs hundreds of Agents and Tools and
thousands of invocations per day, retaining millions of audit events per year;
five user roles; P1 delivery covers User Stories 1–3.

**Structure Decision**: a monorepo with two product applications (`apps/api`,
`apps/web`) and three supporting services (`services/gateway`,
`services/runner`, `services/worker`). The control plane is a **modular
monolith**, not microservices: it keeps one transaction boundary for governance
state while forcing strict layering inside `apps/api`. The gateway and runner are
separate deployables because they sit on the invocation path, must scale and be
isolated independently, and must be able to fail closed without taking the
control plane down with them. Shared contracts live in `libs/contracts` and are
generated from OpenAPI and the event schemas rather than hand-duplicated.

Two properties are load-bearing. First, **Agents never reach tools directly**:
the MCP gateway is the only path, and it is where authentication,
authorization, policy, approval and audit are applied in that order. Second,
**the enforcement path fails closed**: if OPA, the approval store or the audit
sink cannot be reached, the invocation is denied and the denial is recorded
when the dependency recovers.

## Module Responsibilities, Dependencies and Call Chains

| Module | Responsibility | Depends on | Notes |
|--------|----------------|------------|-------|
| Identity & Access | Users, roles, organisations, session and token validation | Keycloak, Postgres | Owns the five role definitions and scope checks |
| Agent/Tool/Model Registry | Register, version, own, retire Agents, Tools and Models | Postgres, audit | Rejects incomplete/duplicate entries; emits change events |
| Policy Center | Author, version and publish Rego policies; evaluate decisions | OPA, Postgres, Redis cache | Deterministic, deny-by-default; records matched policies |
| Approval Center | Raise, route, decide and expire high-risk approvals | Postgres, worker, audit | Immutable decisions; idempotent per request |
| Audit Center | Append-only tamper-evident event store, search and export | Postgres, object storage | Separate write path from application logs |
| Evaluation Center | Evaluation tasks, versioned datasets, reports | Runner, object storage | Datasets immutable once used |
| Release Center | Release, canary, promote, rollback, decommission | Registry, policy, audit | Gate on blocking evaluation failures |
| Dashboard | Operational status, risk events, governance metrics | Audit read model, Redis | Read-only; figures reconcile with audit data |
| MCP Gateway | Single enforcement point for every tool invocation | OPA, Vault, Postgres, Redis, Runner | Fails closed; never bypassed |
| Isolated Runner | Execute tool adapters under isolation and egress policy | Vault, object storage | Separate sandbox class per risk level |
| Worker | Expiry, outbox relay, canary automation, evaluation dispatch | Postgres, Redis Streams | At-least-once with idempotent handlers |
| Web SPA | Operator and approver experience | Control-plane API | Never talks to the gateway or runner directly |

**Layering inside the control plane** (dependencies point inward only):
`interface` → `application` → `domain` ← `infrastructure`. Routers may not
contain business rules; domain code may not import infrastructure, HTTP or
database libraries. This is enforced by an import-linter check in CI, so
Principle I is mechanically verified rather than asserted.

### Primary call chains

1. **Allowed invocation (low/medium risk)**: Agent → Gateway `authN` → `authZ`
   → OPA decision → Runner sandbox → tool adapter → audit event → result.
2. **High-risk invocation**: Agent → Gateway (authN/authZ/policy) → risk
   classified high → Approval request created → *hold* → Approver decides →
   decision recorded → Gateway resumes with the request's idempotency key →
   Runner in a dedicated sandbox → audit event → result.
3. **Registry change**: SPA → API `interface` → `application` use case →
   `domain` validation → repository → transactional outbox → audit event →
   Redis Stream consumers.
4. **Policy change**: SPA → API → Rego validation (OPA test suite) → policy
   version stored → bundle published → cache invalidation → subsequent
   decisions cite the new version.
5. **Audit investigation**: SPA → API → audit read model → filtered query →
   export job → object storage → signed download link.

Critical indexes (rationale, not just columns):

- `invocation (organisation_id, created_at DESC)` — audit and dashboard scans.
- `invocation (organisation_id, idempotency_key) UNIQUE` — guarantees
  at-most-once execution for retried requests (FR-022, edge case "duplicate
  request").
- `audit_event (organisation_id, occurred_at DESC)` — the primary audit query.
- `audit_event (organisation_id, actor_id, occurred_at DESC)` — actor
  investigation.
- `audit_event (organisation_id, target_type, target_id, occurred_at DESC)` —
  reconstructing one operation end to end (FR-026).
- `approval_request (organisation_id, status, expires_at)` — the worker's
  expiry sweep and the approver's pending queue.
- `approval_request (organisation_id, invocation_id) UNIQUE` — one approval per
  invocation, preventing duplicate approvals on retry.
- `policy (organisation_id, agent_id, tool_id, environment)` — decision lookup.
- `agent_version (agent_id, version) UNIQUE` and `agent (organisation_id, name)
  UNIQUE` — duplicate registration rejection (FR-009).
- Partial index `tool (organisation_id) WHERE risk_level IN ('high','critical')`
  — fast high-risk inventory for the dashboard and approval routing.
- GIN on `audit_event.detail` (JSONB) — filtered search without table scans.

All tenant tables carry `organisation_id NOT NULL` and a row-level-security
policy keyed on the session's organisation claim; this is the mechanism that
makes FR-036 true regardless of which deployment model is confirmed.

### Authentication, Authorization, Auditing and Key Management

- **Authentication**: human users authenticate through Keycloak via OIDC
  (authorization code + PKCE); the SPA holds short-lived access tokens and
  refresh tokens. Agents authenticate with a client credential whose private
  key never leaves Vault; each Agent identity is bound to an `agent_version`.
  Service-to-service calls use workload identity (mTLS in Kubernetes, shared
  network identity in Compose).
- **Authorization**: role-based permissions (the five roles) checked at the API
  boundary, plus scope checks (`organisation_id`, `agent_id`, `tool_id`).
  Deny by default; an unmapped action is refused. Approval authority is a
  distinct permission, not implied by administrator status.
- **Policy enforcement**: OPA evaluates Rego over a decision input containing
  the actor, Agent, Tool, risk level, environment, time window and the resolved
  grants. Decisions are cached per (agent, tool, policy version) with a short
  TTL; every decision records the policy version applied (FR-015).
- **Auditing**: `AuditEvent` rows are written in the same database transaction
  as the change they describe, then chained: each row stores
  `prev_hash`/`entry_hash` over its canonical fields. A nightly verification job
  recomputes the chain and raises a risk event on any mismatch. Audit writes do
  not depend on the message bus, so a bus outage cannot lose audit records.
- **Key management**: all secrets and key material live in Vault (KV v2 for
  credentials, Transit for encryption and signing). No secret is stored in
  Compose files, Helm values, environment defaults or the repository. Database
  columns holding sensitive values use application-level encryption with
  Vault-managed keys and are rotated on a defined schedule; on-premises
  installations may back Vault with an HSM via PKCS#11.
- **Least privilege**: each service has its own database role with the minimum
  grants; the runner has no direct database access at all and reaches the
  platform only through narrow, audited interfaces. Standing administrative
  database access is not used by application paths.

### Development Environment Startup and Deployment

Development uses Docker Compose with the following services: `postgres`,
`redis`, `opa`, `vault` (dev mode), `keycloak`, `api`, `gateway`, `runner`,
`worker` and `web`. Startup, migration, seeding and verification steps are in
[quickstart.md](./quickstart.md); the quickstart doubles as the acceptance
walkthrough for the P1 stories.

Deployment:

- **Development / single-node private install**: Docker Compose profile with a
  single-node Postgres and Redis, HTTPS terminated by an ingress container.
- **On-premises production (reserved)**: Helm charts in `deploy/helm` targeting
  Kubernetes. The runner uses a distinct node pool and runtime class so that
  high-risk sandboxes are separated from the control plane at the node level,
  not only by container flags.
- **Air-gapped operation**: all images and the OPA bundle are mirrored into an
  internal registry; there is no mandatory outbound egress. Vulnerability
  scanning and dependency mirrors run inside the environment.

### Key Technology Selections and Alternatives

| Area | Selected | Alternatives considered | Why |
|------|----------|-------------------------|-----|
| Control plane | Python + FastAPI | Django REST, Litestar | Async I/O, typed request/response models, OpenAPI generated from code, minimal ceremony for a governance API |
| Persistence | PostgreSQL 16 + SQLAlchemy 2.0 + Alembic | MySQL, SQL Server | Row-level security for tenant isolation, JSONB for event detail, mature migration tooling, mature on-prem footprint |
| Cache / short-term state | Redis 7 | Memcached, in-process cache | Needed for locks, rate limits and Streams, not only key/value caching |
| Frontend | React 18 + TypeScript + Vite | Vue, Angular | Team fit and the richest ecosystem for admin consoles; Vite for fast feedback |
| Agent workflow | LangGraph | Temporal, Airflow, bespoke state machine, direct framework calls | Explicit graph/state model fits approval-gated workflows; a decision that remains reversible — Temporal is the fallback if durability requirements grow (ADR-0004) |
| Policy engine | OPA / Rego | Cedar, custom DSL, database rules | Mature, testable policy-as-code with a bundle distribution model and a sidecar deployment story (ADR-0005) |
| Tool integration | MCP gateway | Direct adapters, bespoke RPC | The gateway gives one enforcement point for authN/authZ/policy/audit (ADR-0003) |
| Runtime isolation | Container sandbox, dedicated sandbox class for high risk; gVisor runtime class on Kubernetes | MicroVM (Firecracker), separate cluster per risk tier | Strong isolation with an operationally realistic path from Compose to on-prem Kubernetes; microVMs remain an upgrade path (ADR-0006) |
| Identity | Keycloak (OIDC) | Auth0, Okta, Entra ID | Self-hostable and air-gap friendly, which the private-deployment requirement demands |
| Secrets and keys | HashiCorp Vault | Cloud KMS, Kubernetes Secrets | Works on-prem and air-gapped; Transit gives application-level encryption without external callouts |
| Eventing | Transactional outbox + Redis Streams | Kafka, RabbitMQ, Postgres LISTEN/NOTIFY | Correctness first (outbox), simple operationally at the initial scale; Kafka is the documented scale-out path |
| Migrations | Alembic, expand/contract | Raw SQL scripts, framework auto-migrate | Versioned, reviewable, deterministic (ADR-0010) |

### Feasibility, Module Boundary and Security Risk Verification

Performed before any business code is written, as requested.

**Feasibility**

- The stack is conventional and fully self-hostable: FastAPI, PostgreSQL,
  Redis, OPA, Keycloak and Vault all run on-premises and air-gapped, which is
  the constraint most likely to invalidate a plan of this kind. No component in
  the critical path requires external egress.
- The one genuinely uncertain dependency is the MCP ecosystem's maturity for
  enterprise gateway use. Phase 0 must prove a gateway round trip; ADR-0003
  records the fallback (a thin bespoke gateway over the MCP SDK with the same
  enforcement contract) if the reference implementation cannot meet the
  audit and fail-closed requirements.
- LangGraph's durability model is adequate for approval-gated workflows at the
  initial scale but is not a general workflow engine; ADR-0004 states the
  measurable trigger for revisiting this (long-running work exceeding in-memory
  checkpoint expectations, or a requirement for cross-process resumability at
  scale) and names Temporal as the alternative.

**Module boundaries**

- The gateway and runner are the only components on the invocation path, and
  the control plane is not. This means a control-plane outage degrades
  administration but cannot open a path around enforcement — the boundary is
  drawn so that the security property survives partial failure.
- Inside the control plane the layering is enforced by an automated import
  check rather than convention, so the boundary cannot silently erode.
- The runner has no database credentials. Any coupling between the runner and
  governance state must be expressed as an audited interface, which prevents
  the isolation boundary from becoming a back door.
- Risk of over-coupling: the dashboard reads from the audit read model rather
  than joining live operational tables, so reporting load cannot destabilise
  the enforcement path.

**Security risks and mitigations**

| Risk | Impact | Mitigation |
|------|--------|------------|
| Enforcement bypass (a caller reaches a tool adapter directly) | Total loss of governance | Gateway is the only egress for tools; runner has no inbound route from the SPA or agent; network policy denies lateral access; CI test asserts no direct adapter route exists in production configuration |
| Policy engine unavailable and defaulting to allow | High | Fail-closed decision path with an explicit denial reason; a test forces an OPA outage and asserts denial |
| Approval replay or duplicate execution via retry | High | Unique idempotency key per invocation; approval bound to exactly one invocation; uniqueness constraints in the database, not only in application code |
| Self-approval or privilege escalation through role blending | High | Approval authority as a separate permission; self-approval refused by default and policy-gated; explicit security tests per role matrix |
| Tenant data leakage through a missing scope filter | Critical | `organisation_id` non-null on every aggregate plus row-level security, so an unfiltered query still cannot cross tenants; isolation tests per entity |
| Audit tampering or gaps | High | Hash-chained append-only rows written in the same transaction as the change; nightly verification; audit writes independent of the message bus |
| Secret exposure through configuration or images | High | Vault-only secrets; gitleaks and configuration checks in CI; no secret material in Compose or Helm sources |
| Prompt/tool injection leading to unintended tool use | High | Tool permissions are declared and enforced at the gateway, not inferred by the model; high-risk tools always require approval regardless of model intent |
| Sandbox escape from untrusted tool code | High | Dedicated sandbox class and node pool for high-risk execution, restricted syscalls, no ambient credentials, egress denied by default |
| Rollback leaves split-brain state | Medium | Rollback is a recorded state transition with a defined recovery target; a failed rollback raises a risk event and pins the system to a known state |
| Notification/approval latency blocks business flows | Medium | Expiry with explicit recorded outcome; configurable windows; dashboards surface approval latency as a first-class metric |

**Not addressed by this plan (deliberate)**: final risk-classification rules,
approval routing matrix, retention periods and data-residency rules remain open
business rules carried from the specification. They change configuration and
policy content, not the architecture, with one exception — if data residency
requires per-region deployments, that is a deployment-topology decision to be
made before Phase 7.

# Implementation Plan: Permission Center

**Branch**: `002-permission-center` | **Date**: 2026-10-14 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/002-permission-center/spec.md`

**Note**: This plan is filled in by the `$speckit-plan` command. It is a design
artifact; no application business code is generated by it.

## Summary

Build the administration and enforcement layer for authorisation over Agent
Registry resources. An administrator creates roles, binds permissions to them,
assigns roles to people within a scope, and records who is accountable for each
Agent. Every request to a protected capability is verified against the caller's
effective permissions before it takes effect, and every change to that answer is
recorded permanently.

The design reuses what the platform already has rather than building a parallel
identity system: `organisation`, `user`, `role` and `role_assignment` exist in
migration `0001_identity`, and permission changes are recorded in the existing
append-only `audit_event` trail from `0002_audit_event`. This feature adds the
permission catalogue, the role-to-permission binding, and Agent responsibility —
and a decision component that RBAC uses today and attribute-based rules can
extend later without redesign.

## Technical Context

**Language/Version**: Python 3.12 (control plane); TypeScript 5.6 for the console

**Primary Dependencies**: FastAPI, Pydantic v2, SQLAlchemy 2.0 (async), Alembic,
asyncpg; OPA/Rego (ADR-0005) as the decision component; React 18, Vite, TanStack
Query, Ant Design for administration screens

**Storage**: PostgreSQL 16. No new store: permissions reuse `0001_identity` and
audit reuses `0002_audit_event`. Redis is used only for short-lived permission
decision caching, keyed per organisation and per role version

**Testing**: pytest, Schemathesis against the committed contract, testcontainers
for PostgreSQL and OPA, the existing in-memory port adapters for use-case tests,
Vitest and Playwright for the console

**Target Platform**: Linux containers; Docker Compose for development, Helm on
Kubernetes for on-premises

**Project Type**: Web application; this feature is a new module inside the
existing control plane, plus console screens

**Performance Goals**: p95 permission decision under 50 ms on the request path,
since it runs on every protected call; p95 administration read under 300 ms;
cached decisions must be invalidated within one verification of a change (FR-020)

**Constraints**: deny by default; fail closed when the decision cannot be made;
tenant isolation enforced in the data layer; permission-change records are
permanent; the five built-in roles are immutable baselines (FR-031)

**Scale/Scope**: hundreds of users, dozens of roles and thousands of assignments
per organisation; a permission catalogue in the low hundreds of entries

not an enforcement hop, and the enforcement path already lives in the gateway.

## Boundary with feature 001

The two features overlap, so the split is fixed here rather than left implicit:

| Concern | Owner |
|---------|-------|
| The five built-in roles and their fixed permission matrix | **001**, unchanged. 002 treats them as read-only baselines (FR-031) |
| The authorisation dependency that guards a route | **002** extends it to resolve *effective* permissions, replacing the static role lookup. 001's routes inherit the change without modification |
| The permission catalogue and role-to-permission binding | **002** |
| Scoped, time-bound role assignments | **002** administers them; the `role_assignment` table they use already exists in `0001_identity` |
| Assignment expiry enforcement | **002**, at the point effective permissions are resolved |
| Agent responsibility and resource-scoped authorisation | **002** |
| The gateway's invocation enforcement | **001**, unchanged. 002 supplies the answer, not the call path |

The last row is not free: the control plane must not sit on the invocation path,
because enforcement has to survive a control-plane outage. The Permission Center
therefore **projects its policy data into the bundle** the gateway already
consults, refreshed on every change, rather than exposing a decision endpoint the
gateway would have to call. T060 owns that work; without it, tool invocation would
keep a static check while the console used the new one.

This is the one architectural decision that could have gone either way, and it is
recorded in
[ADR-0011](../001-agent-governance-platform/adr/ADR-0011-authorization-decision-component.md)
as part of this feature.

## Decision Component: RBAC Now, ABAC Later

ADR-0005 makes OPA the single source of truth for allow/deny decisions, and the
platform already ships a policy bundle for tool invocation. Authorisation for the
Permission Center uses the same component rather than adding a second rule engine:

1. The control plane resolves the caller's **effective permissions** — role
   permissions plus assignments, filtered by scope, expiry and organisation — and
   assembles them into a decision input.
2. OPA evaluates `deploy/policy/authorization.rego` over that input and returns a
   decision with the sources that contributed.
3. The decision is cached briefly, keyed by organisation and by a role-version
   token, and invalidated whenever a role, permission or assignment changes
   (FR-020).
4. Fail closed: if OPA is unreachable, the request is refused and the refusal is
   recorded with `degraded_mode`, exactly as the gateway does for tool calls.

Attribute-based rules extend this by adding fields to the decision input — a
resource's data class, the request's environment, the caller's region — and new
rules in the bundle. No change to roles, assignments or stored decisions is
required, which is what FR-028 asks for. The input document is versioned so a
past decision remains replayable.

## Testing Strategy

| Layer | Scope | Tooling |
|-------|-------|---------|
| Unit — domain | Permission catalogue rules, scope and expiry resolution, built-in role immutability, least-privilege invariants | pytest |
| Unit — application | Create role, bind and unbind permission, assign, revoke, transfer responsibility, against in-memory ports | pytest |
| Policy | RBAC decisions: allowed, denied by omission, denied by explicit rule, deny-beats-allow, expired assignment, out-of-scope Agent | `opa test` |
| Contract | Every new endpoint against the committed contract | Schemathesis |
| Integration | Permission and binding persistence, RLS across organisations, duplicate assignment, role in use cannot be deleted | pytest + testcontainers |
| Security | The four user types against every permission route; revoked permission takes effect at the next verification; fail-closed when OPA is unavailable | pytest suite |
| End to end | Administrator creates a role and binds a permission; developer is refused on an Agent they do not own; auditor is refused every write | Playwright |

## Risks

| Risk | Severity | Mitigation |
|------|----------|------------|
| Caching a decision after a revocation silently grants access (breaks FR-020) | High | Cache key includes a role-version token invalidated on every change; a test asserts a revoked permission is refused on the very next request |
| Effective-permission resolution becomes an unbounded query on the request path | High | Resolve once per request, cache the result, and index the assignment lookups; the p95 budget is 50 ms and is measured |
| Built-in roles drift from feature 001's matrix (FR-031) | Medium | Built-ins are seeded by migration and asserted immutable in the domain; a test fails if any of the five is edited or retired |
| Two specifications both assume they own enforcement | Medium | Resolved in the Boundary section above and recorded in ADR-0011 |
| Administration screens expose a role or assignment outside the caller's organisation | High | RLS on every permission table plus composite foreign keys, as in the registry schema; isolation tests per entity |
| Permission catalogue grows into an unmaintainable list | Medium | Permissions are named and described (FR-007) and grouped by resource; a review step checks that a role does not bundle unrelated capabilities (FR-026) |
| A second decision component is introduced later, by accident | Medium | ADR-0011 records OPA as the single decision authority, consistent with ADR-0005 |

## Feasibility and Verification Limits

Feasible with what exists: the identity and audit schema already provide users,
roles, assignments and an append-only trail; OPA and its bundle already exist; the
layering, error contract and authorization dependency are established. The new
work is one migration, one module, one Rego file and the console screens.

Two things cannot be verified in the current environment, and must not be
reported as verified when they land:

- **The migration.** PostgreSQL and Alembic are unavailable, so `alembic upgrade
  head`, the RLS policies and the composite keys are reviewed design only.
- **The Rego bundle.** No `opa` binary is available, so `opa test` cannot run.
  The RBAC rules must be treated as unverified until it does.

Unit and use-case tests against in-memory ports do run and are the evidence that
should be relied on meanwhile.
